## Context

当前 H5 与微信小程序都读取 `/api/topics`，但 Fastify 每次启动都从 `server/topic-catalog.ts` 构造内存 `Map`。现有 `TopicEditorialQueue` 已表达草稿、候选、拒绝、发布和更正，却没有持久化、管理 API、身份或后台；客户端还会再次按内容类型混排。文章 AI 使用 DeepSeek Chat Completions，而 DeepSeek V4 已另行提供支持服务端 `web_search` 的 Responses API。

目标运营者第一阶段只有一名。运营输入不是新闻采集任务，而是编辑主动提供的一段话题引子、一个或多个链接或两者；AI 形成与现有种子条目相同结构的完整候选，编辑承担最终事实与表达确认。用户作品继续只存在本机，话题后台不得接收正文、采访回答或备份。

## Goals / Non-Goals

**Goals:**

- 在不部署代码的情况下完成话题新增、审核、修订、五席排期、提前下线和历史追踪。
- 用独立 SQLite 在单机部署中可靠保存话题、后台身份、会话、生成记录和审计，并支持迁移、检查、备份与回滚。
- 通过 DeepSeek Responses API 提供显式触发、默认联网、结构化且永不自动发布的候选生成。
- 保持公开话题协议、作品快照和旧备份可读，同时允许零来源和少于五条热门。
- 让后台有独立登录和安全写边界，不依赖受控体验者的 Basic Auth。

**Non-Goals:**

- 自动抓取、定时发现、无人审核发布、行为热度排序、用户投稿、评论或社区。
- 多管理员角色、找回密码、云端作品、跨设备同步或小程序内管理后台。
- 本次连接服务器、修改 DNS、上传或发布小程序。

## Decisions

### 独立 SQLite 与不可变发布修订

话题与管理员数据使用单独的 `topics.sqlite`，不与微信身份库混表。数据库启用 foreign keys、busy timeout、WAL、FULL synchronous、STRICT 表、schema version 和启动 `quick_check`。生产路径必须为绝对路径；开发默认使用 Git 忽略的 `.data/topics.sqlite`。

稳定话题、修订、生成记录、首页席位、管理员、会话和审计分别建表。来源、角度和标签随修订保存；草稿/候选可携带 optimistic revision token 更新，发布/更正修订一旦冻结便不可原地编辑。更正从最新正式修订复制为新候选，发布后成为更高 revision。

选择 SQLite 是因为当前单机、单编辑、低写入量，且仓库已有 Node SQLite 的迁移与恢复模式。此阶段不引入 PostgreSQL 或 ORM；存储通过仓储接口隔离，未来可迁移。

### 查询时间驱动排期

首页只有 1–5 五个显式席位。每条排期保存修订、开始和可选结束时间；同席位重叠由事务拒绝。公开列表在查询时计算当前有效席位，因此服务停机跨过上线时间后也能正确恢复，不需要常驻 cron。没有接档的席位保持为空，不自动用其他话题补齐。

`publishedAt` 未来、`expiresAt` 已过、状态归档或排期未生效的内容不进入公开列表。详情返回已生效的最新正式修订；无来源时客户端不渲染来源区。公开列表保留既有响应包络和查询参数，但最多只会返回五条，且顺序就是席位顺序。

### 编辑引子与 DeepSeek Responses API

生成请求接受 0–6000 字引子、0–5 个 HTTP(S) 链接和联网开关，文字或链接至少一项。仅链接输入必须联网；关闭联网时不发送任何工具声明。开启联网时使用 DeepSeek `/responses` 和 `web_search`；含链接时明确要求阅读链接，纯文本时允许模型按需搜索。

一次顶层请求使用 JSON Schema 输出一套候选：类型、标题、摘要、内部判断、相关切面、首问、标签、建议有效期和可选来源。服务端再次以 Zod 校验并只保存可验证字段，不保存 reasoning。模型名、token、联网标志、搜索调用数和固定错误类别进入生成记录。全局只允许一个后台生成请求，不自动重试；失败保留编辑输入，手工草稿始终可用。

文章小文仍走现有 Chat Completions。分开适配避免把搜索、后台审计或话题 schema 引入用户文章请求。

### 单编辑应用身份

后台使用独立登录页。用户名和 scrypt 密码散列来自 root-only 环境文件；交互式脚本从隐藏 stdin 读取密码并只输出散列。随机会话 token 只以 SHA-256 保存，Cookie 为 HttpOnly、SameSite=Strict，生产 Secure；会话设定固定过期、显式退出和凭据指纹，密码散列变更后旧会话失效。

所有管理读取都需会话，写请求还需精确 Origin、JSON Content-Type 和会话 CSRF token。登录按 IP 限流，错误不区分账号或密码。Nginx 为 `/admin/` 与 `/api/admin/` 提供独立路由并关闭外层体验 Basic Auth，应用身份成为唯一后台授权；公开用户入口的保护不变。

### 后台作为独立 Vinext 页面

`/admin/topics` 使用独立客户端页面和样式，不加入产品底部导航。桌面以列表、表单、预览和五席排期为主要布局；390px 手机以单列保留全部数据，重点保证查看、排期和紧急下线。表单先在内存保留编辑值，保存采用版本前置条件，`409` 时显示刷新/复制补救而不覆盖。

### 现有目录只作一次种子

新库为空时在迁移事务中导入现有 21 条记录，并用迁移当时的 `selectHomeTopics` 结果建立首批五席。导入有唯一 migration marker，可重复启动而不重复。之后公开运行只读数据库；静态目录保留为迁移种子和测试夹具，数据库不可用时返回 503 而不回退种子。

## Risks / Trade-offs

- [DeepSeek 搜索结果或结构化输出不准确] → 所有结果仅为候选，字段可编辑，人工发布是唯一公开边界；格式失败不保存半成品且不自动重试。
- [联网搜索可能产生额外 token 与多轮工具调用] → 仅由编辑点击触发、默认可关闭、并发为一，保存 usage 与搜索次数；常规测试不联网。
- [移除域名白名单增加不良链接风险] → 只允许 HTTP(S)、限制长度与数量、React 转义显示、外链安全打开，并由已登录编辑对最终来源负责。
- [SQLite 单机限制未来多实例] → 当前部署只运行一个网关写者；仓储接口隔离，扩容前再迁移数据库。
- [独立后台暴露登录入口] → 应用层会话、scrypt、限流、CSRF、Origin、严格 Cookie 和无差别错误共同保护，日志不记录凭据。
- [静态目录迁移后回滚旧代码] → 激活前备份并验证话题库；旧代码回滚不会删除库，新代码重新激活时继续读取原数据。

## Migration Plan

1. 创建并离线验证 schema、迁移、种子导入和仓储；不改变现有公开运行时。
2. 切换公开话题路由至数据库并同步 H5/小程序顺序、零来源及备份 schema 回归。
3. 增加后台身份、管理 API、AI 适配和页面，完成本机浏览器与一次有界真实搜索验证。
4. 更新环境、Nginx、systemd、激活/回滚脚本，使未来部署先备份并 quick-check 两个 SQLite 库。
5. 本地检查、构建、迁移恢复和敏感信息扫描全部通过后归档本 change；部署由后续单独授权执行。
