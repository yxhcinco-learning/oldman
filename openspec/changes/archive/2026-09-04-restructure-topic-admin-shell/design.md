## Context

话题后台已具备登录、内容审核、AI 生成、五席排期、历史审计和运行监控，但当前 `TopicAdminApp` 以单文件条件渲染和偏展示型双栏为主。用户明确指出其不像标准后台，并确认采用成熟企业管理台的视觉与信息架构。面向用户前台的 `DESIGN-SYSTEM.md` 不约束后台，后台视觉与交互基线由本变更独立定义。此次仅调整后台壳层和视图组织，必须复用现有接口、会话、状态模型与错误处理。

## Goals / Non-Goals

**Goals:**

- 建立稳定、可辨识的管理后台壳层和工作台首页。
- 让话题列表、筛选、状态与操作在宽屏上以数据表格高效呈现。
- 用详情抽屉承载编辑和预览，避免列表与大型空详情区长期争抢宽度。
- 统一各模块的页面头、工具栏、卡片、表格、状态、错误和空态。
- 在 390px 宽度保持导航、排期与紧急下线完整可用。

**Non-Goals:**

- 不改变 API、数据库、状态流转、认证、排期算法或审计边界。
- 不引入第三方后台组件库、远程字体、分析服务或新的构建依赖。
- 不把后台并入用户端导航或小程序，也不部署到受控服务器。

## Decisions

### 使用单一响应式后台壳层

桌面使用 232px 深色固定侧栏、56px 白色顶栏和浅灰主工作区；侧栏按“工作台 / 内容管理 / 系统”分组。手机保留顶栏并通过菜单按钮展开覆盖式侧栏，主内容不保留桌面侧栏宽度。选择这一结构是因为导航位置稳定、模块层级清晰，也符合高频管理任务的肌肉记忆；不再使用移动端横向栏目，因为栏目增多后难以发现且不易表达分组。

### 工作台只聚合现有数据

工作台从已经加载的话题、席位和现有能力状态计算状态数量、当前席位、最近更新及快捷入口，不新增统计接口，也不伪造趋势、访客或业务指标。这样可以提供管理入口，同时保持数据语义真实。

### 话题列表采用表格，详情采用抽屉

桌面列表占满主工作区，以标题、类型、状态、修订、发布时间和操作构成表格；筛选位于同一工具栏。点击标题或“查看”打开右侧抽屉，抽屉内部以“编辑 / 用户端预览 / 修订记录”切换内容。移动端表格转换为带字段标签的紧凑列表行，抽屉占满屏幕宽度。相比固定双栏，这能让目录管理获得足够横向空间，同时只在需要时进入详情。

### 复用组件与原生 SVG 图标

在现有功能目录内增加轻量图标、页面头、状态标签、抽屉等局部组件，继续使用 CSS Modules，不新增 UI 框架。图标用 `currentColor` 的内联 SVG，避免 Unicode 字符在不同系统出现字形偏差。用户端预览区域显式切回 Echoes 字体与色彩，其他后台区域使用系统无衬线。

### 保持现有请求与状态边界

认证加载、CSRF 请求封装、409 补救、30 秒监控刷新和所有命令接口保持原实现语义。导航切换只改变前端视图，不增加 URL 子路由，避免扩大本轮路由和服务端范围。

## Risks / Trade-offs

- [单文件页面继续增长] → 在同一功能目录拆出图标和纯展示组件，但不为本轮引入全局组件体系。
- [抽屉中的长表单在小屏滚动较深] → 使用固定抽屉头、单一内部滚动区和底部安全留白，主要操作保持可达。
- [工作台数据不是长期趋势] → 明确命名为“当前内容概览”，只显示可从现有数据证明的数量与状态。
- [视觉变化影响既有 UI 测试] → 保留原有可访问名称并新增工作台、表格、抽屉和手机导航语义测试。

## Migration Plan

1. 先在增量规范和本设计文档中确认独立后台基线。
2. 重构后台壳层和话题列表/详情，再迁移其余现有视图到统一页面结构。
3. 补齐 UI 自动化测试并执行完整检查、构建和指定尺寸浏览器回归。
4. 若需回滚，仅回退前端与规范提交；数据库、凭据和话题数据不变。

## Open Questions
