## Context

话题后台当前由单一服务端管理员、scrypt 密码散列、登录限流、服务端会话、精确 Origin 和 CSRF 共同保护。散列生成入口额外规定 12–1024 个字符；用户已明确要求将最小长度放宽到 6，并在本机配置指定账号。本轮不连接受控服务器。

## Goals / Non-Goals

**Goals:**

- 让交互式散列工具接受 6–1024 个字符，并保持既有散列格式和验证路径。
- 用边界测试证明六位可用、五位被拒绝、既有长密码继续可用。
- 仅在 Git 忽略的本机配置中保存账号与散列，重启当前本地后台后完成登录验证。

**Non-Goals:**

- 不保存或打印明文密码，不引入明文环境变量。
- 不改变会话、Cookie、Origin、CSRF、限流、审计或数据库 schema。
- 不部署或更新服务器账号密码。

## Decisions

1. 将密码长度常量集中为 6–1024，并只在散列生成入口验证。验证函数继续从 scrypt 编码读取参数并以恒定时间比较摘要，避免出现第二种凭据格式。
2. 不为六位密码降低 scrypt 成本或放宽登录限流。相较新增 PIN 认证分支，复用现有密码流程能保持攻击面和运维方式不变。
3. 本机实际配置只写入 `.env.local` 的 `TOPIC_ADMIN_USERNAME` 与 `TOPIC_ADMIN_PASSWORD_HASH`。服务端启动仍只读取散列；已在聊天中出现的明文不复制到仓库、配置或日志。
4. 账号轮换沿用现有 credential fingerprint 机制，重启时新用户名或散列会撤销旧会话；浏览器需使用新凭据建立会话。

## Risks / Trade-offs

- [六位密码的搜索空间显著小于十二位密码] → 保留 scrypt 与登录限流，并在文档明确六位是被允许的最低值而非强密码建议。
- [代码规则同样允许未来生产配置六位密码] → 生产激活仍需独立部署授权和 root-only 环境文件；本轮绝不更新受控服务器。
- [本地已有会话在凭据轮换后失效] → 重启服务后立即用新账号完成一次本地登录验证并把已登录页面交给用户。
