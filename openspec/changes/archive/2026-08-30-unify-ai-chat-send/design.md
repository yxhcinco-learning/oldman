## Context

现有 `question` 强制剥离正文，`rewrite` 强制要求完整正文，因此 UI 必须让用户先选择按钮。正文写回已经有独立的候选预览、基准检查和应用确认，可以承担防误改责任，不需要再用双按钮预判意图。

## Goals / Non-Goals

**Goals:**

- 会话只有一个清晰的“发送”操作。
- 同一请求可以返回直接回答或完整候选，问题不会自动改正文，改文也不会被拒绝为“只能回答”。
- 保持旧会话、重试、备份和快捷优化兼容。
- 优化菜单仅保留一个清楚的修改记录入口。

**Non-Goals:**

- 不增加单独的意图分类模型调用或客户端关键词猜测。
- 不允许模型输出绕过预览确认直接写入正文。
- 不改变常规优化和润色文笔的固定任务。

## Decisions

新增持久 action `chat`。服务端在一次 DeepSeek 请求中要求：提问、解释、查找旧内容或意图不明确时只返回 `answer`；明确要求改写、删除、重排或补入用户本轮提供事实时，返回 `answer` 和完整 `body`。客户端不按问号或关键词分类，避免口语表达误判。

控制器依据经过 schema 校验的结果决定 turn 状态：有 `body` 为 `ready` 候选，无 `body` 为 `answered`。`chat` 候选沿用 rewrite 的事实约束、预览、过期检查、事务应用、撤销与恢复，采用后版本来源仍记为 `rewrite`，所以无需升级版本来源或备份 schemaVersion。

旧 `question` 和 `rewrite` 继续存在于 schema、控制器及重试路径，保证已经保存的 turn 可读取和恢复；新 UI 只发送 `chat`。常规优化与润色仍使用固定 action。

优化菜单删除“查看对话记录”，因为会话入口已经呈现全部消息。“修改记录”改成会话入口下方唯一的 48px 次级整行入口；会话页继续在顶部提供同一入口。

## Risks / Trade-offs

- [模型把提问误判为改文] → 结果只形成待应用候选，用户不点击应用就不会改变正文。
- [模型把改文当成提问] → 用户会看到回答而非静默失败，可补充要求后再次发送；提示词明确禁止拒绝清楚的改文要求。
- [统一 action 需要较长输出预算] → 单次请求按候选上限配置，不增加请求次数；真实联调分别覆盖提问和改文。
- [新增 action 影响旧数据] → 枚举只做向后兼容扩展，旧 action 保留，应用后的版本仍使用既有 rewrite 来源。
