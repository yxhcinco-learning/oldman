## Context

当前 `ArticleAssistant` 的 menu、chat 和 preview 都会承担部分 AI 反馈：快捷优化在 menu 发起后直接跳 preview，menu 内又有一套可编辑 composer；会话气泡把 turn 状态放在小文回答之前。底层其实已经将 `result.answer`（修改说明）和 `turn.status`（采纳状态）分开保存，因此无需改服务协议或数据模型，问题主要是页面路由和信息层级。

## Goals / Non-Goals

**Goals:**

- 所有 AI 操作进入同一文章会话，生成进度、小文说明、结果状态和候选入口都在这里出现。
- 优化首页保留快捷选择，但不再承载实际文字输入或生成结果。
- 小文修改说明在候选生成成功时立即可见，并在待应用、已应用、未采用之间切换时保持不变。
- 全文预览继续负责原文对照与确认写回，关闭或返回后回到会话。

**Non-Goals:**

- 不增加第二次模型请求、自动差异分析或逐字高亮。
- 不修改 DeepSeek JSON 协议、IndexedDB/备份版本或已有 turn 数据。
- 不开放精简、扩写、配图、自动应用或语音聊天。

## Decisions

- `answer` 继续作为小文的修改说明，`status` 继续作为候选状态，UI 分别渲染为回答正文和独立状态/操作区。相比新增字段，这能兼容所有既有会话和备份；模型说明的精确程度仍受提示词约束。
- 所有 `run` 动作先切到 chat，并在结果完成后停留 chat；不再由非 question 动作自动调用 `showTurn`。用户通过“查看优化结果/查看调整结果”进入 preview，避免生成完成时页面突然切换。
- menu 中的紧凑 composer 改为具有输入框外观的可访问按钮，只负责打开 chat。实际 textarea 和“问小文/调整文章”操作只保留在 chat，避免两套输入状态和焦点行为。
- 常规优化和润色文笔仍发送原有 action 与空 prompt，不改变服务契约；会话展示层根据 action 生成“常规优化全文/润色全文”的用户操作文字，兼容旧的空 prompt turn。
- preview 的返回目标固定为 chat；应用或放弃也回到 chat，并只更新独立状态。menu 不再重复列出待确认候选，避免反馈分散。

## Risks / Trade-offs

- [用户需多点一次才能看到全文] → 会话直接展示修改说明和明显的“查看结果”按钮；完整预览仍是安全写回所需步骤。
- [旧会话中的空 prompt 形成空白气泡] → 按 action 提供展示用文字，不修改历史数据。
- [修改说明可能过于笼统] → 本次保证说明不会被状态覆盖；不声称提供程序生成的精确 diff，后续可独立增加结构化差异能力。
- [首次同意会暂时进入授权页] → 同意后立即进入会话并显示生成过程，不增加请求。
