## Context

正式编辑器目前由 `WritingToolbar` 提供“语音 / 文字 / 聊天 / 优化”四项：前两项是互斥输入方式，“聊天”只显示未开放提示，“优化”打开 `ArticleAssistant` 的菜单页。用户从菜单选择常规优化、润色文笔或二级小文入口后才进入文章会话。`ArticleAssistant` 已在同一组件内承载会话、候选预览、修改记录、版本查看和首次同意，并通过 `ArticleAiController`、文章版本与 IndexedDB 保证回答和候选的持久化边界。

现有 `chat` action 已能用同一次请求区分只读回答与完整改文候选；`question` action 会在服务端和客户端强制保持只读，`regular`、`polish` 已有独立的受约束任务。移动画布已经使用 `VisualViewport` 变量，文章会话已经使用原生 modal `dialog`、独立消息滚动区、52–148px 自适应输入和点按语音。因而一期的主要工作是重组入口和展示状态、增加两个固定只读意图，而不是建立新的 Agent、存储或请求协议。

本变更发生在 `improve-mobile-writing-assistant` 等既有变更全部归档之后；当前没有活跃变更。它替代现行规范中的优化菜单和聊天占位入口，但必须保留已经上线的常规优化、润色文笔、自由问答/改文、候选确认和修改记录。

## Goals / Non-Goals

**Goals:**

- 让用户在编辑器中只需识别一个“小文”入口，并用同一小按钮槽位交替切换语音/文字输入，与写作伙伴操作清楚分组。
- 打开小文后直接进入同篇文章会话，以紧凑面板保留部分正文背景，并允许显式展开为适合长会话和系统键盘的大面板。
- 会话首页暂不展示预设快捷指令，只保留直白的自由输入、语音和发送；既有只读/改文 action 保持兼容但不占用本期界面。
- 收起面板后保留本次编辑器会话中的未发送输入、文章会话和进行中请求；请求在后台完成或失败时让小文入口提供可访问的状态反馈。
- 保持首次同意、付费请求边界、会话听写、失败补救、版本历史、旧 action/备份兼容及 360–430px 手机可达性。

**Non-Goals:**

- 不实现小文自动捧哏、定时/停顿触发、后台内容分析、自动发送、自动展开或主动语音。
- 不支持空正文时由小文起题，不加入朗读、选区级改写、人物/时间线结构化数据、长期陪伴偏好或跨文章记忆。
- 不开放精简、扩写或配图，也不在一期面板继续展示这些禁用卡片。
- 不新增 AI action、模型调用轮次、数据库字段、备份版本、依赖或外部服务，不修改 DeepSeek 模型和用量上限。
- 不让紧凑面板与编辑器同时可交互；仍使用有焦点约束的模态底部面板，避免双滚动和焦点泄漏。

## Decisions

### 小文替代现有功能入口但不重定义原“聊天”概念

`WritingToolbar` 删除现有“聊天 / 优化”两个 `editor-actions`，改为带叶片图标和“小文”文字的单一操作；这里仅表示一期不保留当前聊天占位并把优化收进小文，不把用户原规划中的“聊天”概念定义为小文。`Editor` 删除 `chatUnavailable` 状态和“聊天功能暂未开放” toast，原优化发现提示改为锚定小文的一次性提示。

选择单一入口而不是把“小文”追加成第五项，是因为当前四项已经混合了输入模式与动作，新入口必须减少而不是增加选择。精简、扩写和配图仍记录为待开放能力，但不再用禁用卡片占据一期的主要界面。

### 主编辑器使用单槽位目标模式按钮

主编辑器不再同时展示“语音 / 文字”两个大页签。`WritingToolbar` 在固定的小按钮槽位中显示“切换后将进入的输入方式”：

- 当前为文字输入时显示麦克风图标，可访问名称为“切换到语音输入”；点击后收起系统键盘、显示现有语音舞台，但不申请麦克风、不自动开始录音。
- 当前为语音输入时显示键盘图标，可访问名称为“切换到文字输入”；点击后进入现有全文 `textarea`，恢复既有光标规则并唤起系统键盘。

该按钮至少 48×48px，图标、森林绿、浅绿纸面色、圆角、焦点和间距完全使用 Echoes 规范；默认不使用纯白底或外投影，避免在浅色工具栏上形成脱离同组控件的悬浮圆点。悬停只做同色系轻微加深。参考截图只提供“同一位置交替显示目标模式按钮”的交互模式，不引入其灰白视觉、完成按钮、表情入口或输入法外观。小文在同一工具区保持独立文字入口，不能与模式切换图标合并。

选择显示目标模式而不是当前模式，是因为正文/语音舞台已经清楚表达当前状态，按钮应直接说明点击结果；同时避免两个常驻大按钮占用手机宽度。模式切换继续复用 `Editor.setMode`，不改变正文、标题、待确认语音或保存语义。

### 会话成为小文首页，保留紧凑与展开两种面板状态

`ArticleAssistant` 删除 `entry` 和 `menu` 页面；打开时直接以 `chat` 为首页，预览、修改记录、版本和同意页返回时都回到会话。标题使用“小文”，不再显示“文章优化”或“和小文聊一聊”两层名称。

面板保存 `compact | expanded` 展示状态。首次打开使用 `clamp(360px, 52dvh, 440px)` 的紧凑高度，短屏也不自动改为接近全屏；页头提供至少 48px、具有“展开小文 / 收起小文”可访问名称的显式操作，用户需要更多空间时再主动展开。拖拽手势不是必需交互。点击输入框只显示完整焦点状态，不改变 `compact | expanded`；系统键盘缩小可视区域时由既有 Visual Viewport 变量与 dialog `max-height` 把当前状态约束在可见区域。消息区在固定页头与输入区之间独立滚动。打开面板不自动聚焦输入框，避免立即弹出键盘。

继续使用原生 modal `dialog`，而不是实现可拖拽自由悬浮窗：手机屏幕和系统键盘下，自由悬浮会遮挡正文、制造两个可交互滚动面并削弱焦点约束。桌面本期也沿用同一底部面板，只通过最大宽度和高度适配，不单独建立另一套窗口组件。

### 收起是最小化，不是取消本次小文任务

从小文首页点击关闭或按 Escape 视为收起面板并恢复“小文”入口焦点。未发送输入提升到 `ProductApp` 的当前作品内存状态，面板重新打开时恢复；发送成功后才清空。该草稿不写入 IndexedDB 或备份，离开作品、刷新或结束编辑时可以清除。

收起面板不调用 `ArticleAiController.cancel()`；进行中请求继续使用已有 controller 和文章会话，完成结果仍落入同篇会话。工具栏小文入口在面板收起时表达“正在处理”，请求完成或失败后表达“有新回复 / 需要处理”，用户重新打开后清除未读状态。离开当前作品、页面卸载或显式点击会话内“取消请求”仍按现有边界终止请求。

预览、同意和修改记录等下级页面的返回按钮仍返回会话；下级页面的关闭/Escape 同样收起整个小文，而不恢复已删除的优化菜单。候选和修改记录已经持久化，因此重新打开回到会话不会丢失结果；未发送输入由上层内存状态保留。

### 会话首页只保留自由输入

会话输入区不展示任何预设快捷指令、能力卡片或相邻教学说明，只保留可编辑文字、点按语音和单一“发送”。用户可以直接描述“问我一个问题”“检查是否讲清楚”或“帮我修改”等需要，由既有 `chat` 单次请求决定只回答、追问或返回待确认候选；不在客户端用按钮或关键词分类，也不增加模型调用。

`regular`、`polish` 以及精确 prompt“接着问我”“讲清楚了吗”的 `question` 契约继续保留，以兼容旧会话、测试和后续可能重新设计的入口。当前正式界面不直接派发这些快捷 action。正文为空、过长或有待确认语音时继续使用现有本地校验，不发送请求。

### 两个只读意图通过 `question` 强制执行

服务端 `question` 系统提示对精确 prompt“接着问我”和“讲清楚了吗”增加专门规则。二者只以 `current.body` 为主要依据，不把历史建议当作当前事实，不调用外部知识，不推断缺失经历；普通文字追问继续沿用既有规则。

选择 `question` 而不是 `chat`，是因为控制器已经会删除 `question` 响应中的意外 `body`，从协议到入库都能保证快捷意图不会形成待应用候选。无需新增 `AiAction`、版本 source 或数据库迁移，旧 `question` turn 继续兼容。若模型仍返回不合规正文，客户端丢弃正文并只保存回答；无有效回答、失败或取消沿用现有失败状态和重试。

### 延续会话输入、隐私和确认边界

自由输入继续通过单一“发送”走 `chat` action，同一次请求决定回答或生成候选；点按语音只把识别文字写入可编辑输入框并由用户显式发送。常规优化和润色结果继续留在会话，状态与小文说明分开，查看全文后才可应用。

首次快捷操作或自由发送仍先显示当前文章、相关修改记录和聊天消息会发送给 DeepSeek 的同意页。打开、展开、收起小文以及显示快捷项本身不发送文章，也不增加计费请求。历史模拟组件继续隔离。

### 更新发现提示而不引入主动内容分析

沿用现有 80 个非空白字符和本机一次性标记，只把提示改为“小文可以陪您接着写，也能帮您整理。”并锚定“小文”入口。提示约 6 秒自动消失，点击小文立即收起，不自动打开会话之外的页面、不生成内容、不调用 AI。

为避免已经看过旧优化提示的用户重新受打扰，继续复用 `suiyue-optimize-tip-v1` 标记；这意味着旧用户不会自动看到新提示，新用户和清理本机数据后的用户会看到。选择兼容旧标记而不是改成 v2，是为了遵守一次性、少打扰的产品意图。

## Risks / Trade-offs

- [“小文”名称对首次用户不如“优化”直接] → 使用一次性发现提示、叶片图标和完整可访问名称；会话内先不增加能力按钮或常驻教学段落。
- [单个图标可能被误解为立即录音或当前模式] → 使用“切换到语音输入 / 切换到文字输入”的完整可访问名称，点击只切换界面；真实录音仍必须在语音舞台显式启动。
- [紧凑面板中历史和输入区争夺高度] → 默认约半屏且不超过 440px，消息区独立滚动；只有用户点击页头操作才切换展示状态，输入聚焦不跳高，键盘出现时以 Visual Viewport 约束当前面板，不缩小 48px 触控目标和正文规定字号。
- [最小化期间请求完成但用户没有看到] → 小文入口暴露处理中、完成或失败状态，重新打开直接看到持久化 turn；不以取消付费请求换取简单状态管理。
- [提升未发送输入会增加跨组件状态] → 只保存当前作品的内存字符串，发送后清空，离开作品即释放；不进入领域模型、IndexedDB 或备份。
- [精确快捷文字可能与用户手动输入相同] → 相同文字获得相同、安全的只读行为属于可接受的一致性；其他自由文字继续由 `chat` 判断。
- [模型可能对“讲清楚了吗”虚构问题或超过三项] → 系统提示限定只依据当前正文和最多三项，自动测试校验契约，产品仍不声称自动事实保证；用户可忽略回答且正文不变。
- [旧 UI 测试大量依赖“文章优化”菜单] → 先改契约测试和共享打开助手 helper，再按新信息架构重写组件断言，保留候选、历史、语音、失败和保存回归。
- [真实系统键盘和移动浏览器的 dialog 高度不同] → 使用现有 Visual Viewport 基础，检查 360×640、390×844、430×932、1280×900，并把 iOS Safari/Android Chrome 真机证据与桌面模拟分开记录。

## Migration Plan

不迁移数据。先增加快捷意图的服务端/控制器契约测试，再重构单槽位输入切换、小文入口、上层小文草稿与状态、文章助手路由和面板样式；随后更新产品边界、设计规范、架构决策与验收记录。旧 `regular`、`polish`、`question`、`chat` turn、版本、备份和 IndexedDB 原样读取。

部署前运行 `npm run check`、`npm run build` 及四尺寸浏览器回归；常规验证使用测试 transport，不调用 DeepSeek。若需要真实验证，只用一篇短小非敏感文章分别调用两个只读快捷意图各一次，并单列费用和结果。

回滚只需恢复旧工具栏、菜单页和提示文案；新产生的 turn 仍是现有 action，旧版本能够继续显示和恢复，不需要数据库降级。任何代码回滚前仍按现有流程导出本机 JSON 备份。

## Open Questions

一期没有阻塞实现的产品问题。紧凑面板的最终高度、展开按钮图形和小文入口“有新回复”的视觉强度在实现时按四尺寸浏览器证据微调，但不得改变本设计的状态、触控和数据边界；内容感知主动回应是否进入二期，应等待一期真实用户的发现率、继续写作率、关闭率和误解率证据。
