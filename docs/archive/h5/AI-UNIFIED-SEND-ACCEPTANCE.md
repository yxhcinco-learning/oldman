# 文章 AI 统一发送 · 本地验收（2026-08-30）

## 范围与设计

原“问小文 / 调整文章”双按钮要求用户先判断自己的话属于提问还是改文，也重复占用适老化界面的操作空间。候选预览和明确应用已经承担防止误改的安全职责，因此会话改为一个至少 48px 高的“发送”按钮。

自由输入统一使用 `chat` action，并且每次发送只请求 DeepSeek 一次：模型可只返回回答，也可同时返回完整正文形成待确认候选；要求不清楚时先简短询问。客户端不做关键词分类，也不增加单独的模型分类请求。返回候选仍不会直接写入正文，只有用户查看全文并选择应用后才执行基准检查和事务保存。

旧 `question` / `rewrite` 会话和重试继续兼容；新的 `chat` 候选应用后沿用 `rewrite` 版本来源，不改变 IndexedDB v2 或 JSON v2。优化菜单删除重复的“查看对话记录”，会话入口下方只保留整行“修改记录”；进入会话后仍可从页头查看修改记录。

## 浏览器回归

在内嵌浏览器以 390×844 复用本机“AI 功能验收（测试文章）”，没有发送模型请求、应用候选或修改正文：

- 优化菜单保留会话入口，删除“查看对话记录”，只显示一个整行“修改记录”；
- 会话输入区只显示一个“发送”，没有“问小文”或“调整文章”；
- 发送按钮约 334×48px，会话页顶部“查看修改记录”仍可达；
- 页面无横向溢出，现有候选、状态和修改说明仍按原层级展示。

## 两次真实 DeepSeek 验证

先估算为两次非敏感短文本请求、总量数千 tokens，不循环、不自动重试。实际仅调用两次：

1. 原文“今天早晨，我去公园散步。”，提问“这篇文章写的是什么时候去公园？”：返回“文章写的是今天早晨去公园散步。”，没有 `body`，按回答保存。
2. 同一原文，要求“把‘今天早晨’改成‘今天清晨’，其他内容不变。”：返回修改说明和完整正文“今天清晨，我去公园散步。”，按待确认候选保存。

两次合计输入 1644 tokens、输出 53 tokens；每次发送各产生一次上游调用。只使用上述虚构短文，没有发送用户文章。联调后重启了本机 3002 网关并以只读状态接口确认 DeepSeek V4 Flash 配置可用，没有追加第三次付费调用。

## 边界

- 模型仍可能误判问题或修改要求；程序不声称自动识别完全准确。
- 即使模型返回正文，也只形成候选，不会绕过预览、应用确认、过期保护和撤销。
- 本次没有升级数据库或备份格式，没有部署，也没有做手机真机验收。
- 原 `productize-local-writing` 的远端、真机和目录清理待办继续保持活跃。
